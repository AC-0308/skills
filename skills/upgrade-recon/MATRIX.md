# 调研矩阵（MATRIX）

九个调研面。每个面注明：查什么、关键动作。分派子代理时按面切分——**一个面一个子代理**，不要让一个子代理跨多个面（上下文互不干扰，卡死时损失也隔离）。Step 1 定域后，叠加下方"域特化要点"。

## 信源优先级（全局适用）

1. 官方一手：升级指南 / changelog 源文件 / GitHub Releases（`[Break]` 小节）
2. 包元数据实测：npm registry（peerDependencies、dist-tags、发布时间）、本地 `npm pack` + 解包 diff；非 npm 生态对应 PyPI/crates.io/apt/yum 等发行版元数据
3. issue tracker：官方仓库升级相关 issue/PR（含 open 状态——**open 的坑比 closed 的更重要**，closed 只说明有解，open 说明你现在就会踩）
4. 社区二手：Stack Overflow、中文社区（掘金/知乎等）——**只当线索不当证据**，AI 生成的假"实战文"在中文社区已实测存在

## 域特化要点（Step 1 定域后取用，不在本域的忽略）

| 域 | 追加的调研重点 | 特有信源 |
|---|---|---|
| 前端 | 打包器兼容、视觉回归、浏览器支持矩阵 | 打包器 issue 区、caniuse |
| Node/后端 | 运行时版本要求、协议/序列化变更、安全门禁 | Node release notes、安全公告（CVE） |
| 数据库/中间件 | 数据/存储格式变更、复制协议、驱动配套、**迁移工具链与回滚窗口** | 官方 migration guide、运维文档 |
| CLI/构建工具 | 配置文件格式变更、退出码/日志格式、CI 上的行为 | 项目模板/脚手架的适配声明 |
| 服务器/系统 | 依赖库联动、配置文件兼容、灰度/回滚窗口、重启语义 | 发行版包变更日志、运维手册 |

## 八个调研面

| # | 面 | 查什么 | 关键动作 |
|---|---|---|---|
| 1 | 官方变更面 | 升级指南 + 目标版本及全部中间版本的 `[Break]`/breaking 段（**minor/patch 的 [Break] 段同样要扫**——破坏性变更不只住在 major 里） | 注意：**升级指南与 changelog 是两份独立文档，可能互有遗漏**——升级指南偏行为影响，changelog 的 [Break] 段更全更细，两处都要抓并交叉比对 |
| 2 | 包结构 | npm 项目：package.json 的 type/exports/main/types 字段 diff、default export 有无、peerDeps 联动；其他生态：入口/导出/依赖锁定的等价物（如 Python 的 __init__ 导出与 setup 依赖约束） | `npm pack` 两个版本本地解包 diff（或等价的发行版包 diff），比读文档可靠 |
| 3 | 类型/接口层 | d.ts 导出清单 diff、被移除/改名的类型与公开 API 签名、moduleResolution 下的报错（TS1203/TS2834/TS1479 族）；非 TS 项目对应公开 API/ABI 层 | 用 tsc 探针实测，别只看类型文件 |
| 4 | issue 踩坑面 | 升级后高频报错、渲染/运行异常、误报为 bug 的行为变化 | 按主题归类 + 排"高频坑名次"；每条附状态（open/closed）和绕过 |
| 5 | 生态兼容 | 封装库/扩展库/驱动的 peer/依赖约束是否放行目标版本；不兼容时的安装方案（legacy-peer-deps/overrides/pin 中间版本） | npm registry API 拿一手 peerDeps；README 与元数据口径不一致时**以元数据为准** |
| 6 | 社区讨论 | 实践复盘、反面案例（AI 幻觉文章） | 无法访问就如实标注；发现的幻觉内容要写进产出警示用户 |
| 7 | 弃用史 | 当前版本 → 中间版本的全部 deprecation；目标版本是否真的移除了它们 | 逐字节 diff 兼容层源文件（如 backwardCompat 类）是最硬的证据；"@deprecated 标记数量变化"是辅助证据 |
| 8 | 已知回归 | 目标版本自己 open 的 bug 清单 | 只收影响升级决策的（阻断性/高频误报），附绕过 |
| 9 | 不可逆变更 | 数据/存储格式、协议、持久化产物的变更；是否有官方迁移工具与逆向路径 | **任何单向门必须单独标出**：数据库/中间件/序列化格式类包此面优先级最高 |

## 分派纪律

- 体力面（1、5、6、7 的抓取部分）→ 廉价模型并行
- 判断面（4 的归因、8 的筛选）→ 视复杂度给主力模型
- 每个子代理 prompt 附带：信源清单 + 兜底 + 产出路径 + 请求预算（每信源 ≤5 次请求，防限流）+ 超时纪律
- **产出统一落 `research/<面名>.md`**，命名与面一一对应，主会话验收时好索引
