# Upgrade Recon（升级侦察）

把有风险的版本升级当作一次**侦察行动**，而不是改一行版本号。

触发门槛看的是**风险信号**而非版本号位：major 是信号本身；minor/patch 同样可能夹带破坏性变更（历史先例：changelog 的 `[Break]` 段出现在 minor 位、破坏性的包格式改造发生在 minor 位）。minor/patch 满足任一信号才走本流程，否则直接升级跑测试。

本技能做两件事：**判定**（这个包能不能升、影响面多大）与**指引**（产出一份数字化分级、带回退开关和验收清单的升级指引文档）。**不执行**升级本身——改代码、跑构建交回给普通 coding 流程。

适用域不限于前端：被升的可以是前端库、后端框架/数据库驱动/SDK、Node/Python/Go 等运行时、CLI 工具、服务器组件、操作系统包。Step 1 先定域，再取对应域的调研面与验收手段——前端的目测清单、后端的迁移演练、服务器的回滚窗口，各有各的打法。

## 三个纪律（全程生效）

- **三角验证**：任何进入产出文档的"事实"，必须至少有两个独立信源，或一个信源 + 一次本地实测。单一信源（哪怕官方）只能作为线索，不能作为定论——官方升级指南漏写 breaking change 是真实发生过的事。
- **验收子代理**：子代理调研的产出一律视为**未验证线索**。主会话必须逐份独立复核硬事实后才可引用（方法见 [VERIFY.md](VERIFY.md)）。
- **防卡死保险丝**：所有网络/IO 命令必须带 `timeout`（默认 ≤60s）。超时即失败，失败就换路径或标注"未确认"，绝不静默重试。网络受限不是耻辱，编造数据才是。

## Step 1 对齐——先和用户确认场景

铺开调研前，必须确认五要素。用户没答的按默认值走并在产出文档中声明。

| 要素 | 问什么 | 默认值 |
|---|---|---|
| 运行域 | 被升的东西属于哪个域：前端浏览器、Node/后端服务、数据库/中间件、CLI/构建工具、服务器/系统组件？**先定域，后续调研面和验收手段都随域取材** | 前端 |
| 耦合方式 | 直连包还是经封装库/ORM/发行版包管理器？用了哪些生态扩展？ | 直连 |
| 升级策略 | 一步到位还是先到中间版本消化弃用？中间版本有数据/格式迁移时通常强制分阶段 | 一步到目标版 |
| 风险信号 | minor/patch 时问：上次升级踩过坑吗？目标版本有 [Break] 段吗？（major 默认全信号） | 有信号才触发本技能 |
| 验证手段 | 前端：自动化测试/截图对比/目测；后端：测试套件/金丝雀/兼容性探针；服务器：演练环境/回滚窗口。**跨域组合（如 SSR 全栈）逐域确认** | 人工验证 |

**完成判据**：五要素齐备（含默认兜底），且用户确认过调研维度清单。没对齐就铺开调研是本技能最大的浪费源。

## Step 2 铺矩阵——并行调研

读 [MATRIX.md](MATRIX.md)，按其中的调研面清单分派并行后台子代理。体力活（抓 changelog、查 npm 元数据、列表格）给廉价模型；判断密集的调研面留给自己。每个子代理的 prompt 必须包含：

- 明确的信源清单与兜底路径（信源 404 时先试镜像再如实报告）
- 产出文件的绝对路径
- "命令失败就如实记录原因，不修改产出目录以外的任何文件"的纪律

**完成判据**：MATRIX.md 中全部调研面都有产出文件，或文件中如实标注了"未确认 + 失败原因"。允许部分调研面无结果——社区沉淀少是常态，谎称"没发现问题"才是事故。

## Step 3 验收——逐份复核

读 [VERIFY.md](VERIFY.md)，对每份子代理报告执行复核：抽取报告中最影响结论的 1~3 个硬事实，**不经过子代理的数据**，独立向一手信源验证（curl API / 本地 npm pack diff / gh api）。发现编造立即整份降级为"不可信线索"并重新调研该面。

**完成判据**：每份被引用进最终产出的报告，至少 1 个硬事实经主会话独立验证通过。子代理卡死时接管其 session 抢救已完成的工作（session 日志里有它已抓到的原始数据），不要全盘丢弃。

## Step 4 分级——映射到四级

把全部发现归入下表，一条都不许悬空。**分级是产出文档的骨架，宁缺毋滥：分不准的宁可降级为"待人工确认"也不要硬塞。**

| 级别 | 定义 | 判定依据 |
|---|---|---|
| 🔴 必须改 | 不改就构建/编译/运行失败 | 实测探针或官方明确声明 |
| 🟡 语义变化 | 代码能跑但行为不同，按实际用法逐点排查 | changelog `[Break]`、源码 diff |
| 🟢 仅观感/可观察回归 | 只影响输出观感或可观察行为：前端视觉、后端日志/性能指标、接口响应细节 | 官方 breaking + 社区反馈 |
| ⚠️ 已知未修 | 目标版本自身的 open bug，附绕过 | issue tracker 现状 |

每条 🔴/🟡 必须附**修法或回退开关**；每条 ⚠️ 必须附**绕过方案**（回退开关、替代配置或"暂不使用该特性"）。**不可逆变更（数据迁移、存储格式、协议升级）单列一节**：它不是"改代码"能解决的，需要迁移计划 + 恢复方案，见 OUTPUT.md。

**完成判据**：无悬空条目；每条变更都能回答"谁会中招 + 中招了怎么处理"。

## Step 5 产出——写升级指引

读 [OUTPUT.md](OUTPUT.md)，按模板产出最终文档，落在本工作目录根（旁挂 `research/` 目录存调研底稿并在文末索引）。必须包含：

- TL;DR + 影响面分级总表
- 带验收标准的分步升级 checklist（每步可判定"过/不过"）
- 人工验收清单（验证手段为纯人工时，这是最后的安全网；形式随域取：前端目测项、后端可观察指标项、服务器演练项）
- 不可逆变更的迁移与恢复方案（若有：数据迁移步骤、双向兼容期、演练环境验证）
- 回滚策略（注意：代码回滚 ≠ 数据回滚 ≠ 服务回滚——持久化产物可能让旧版本无法恢复，服务降级可能需要窗口期）

**完成判据**：文档自包含——一个没参与本会话的工程师拿它能独立执行升级。最后通读一遍，问自己"哪句话是子代理没验证过、我也没验证的"，找到就删掉或标注未确认。
