# 产出模板（OUTPUT）

升级指引文档的骨架。目标读者：**没参与调研过程的工程师**，拿文档能独立执行升级。落盘为 `<包名>-<旧版>-to-<新版>-升级指引.md`，放工作目录根；调研底稿旁挂 `research/` 并在文末索引。

## 必备章节与骨架

### 0. TL;DR + 影响面分级总表

5~6 条一句话结论（API 层动没动 / 最大的工程变更是什么 / 哪个策略对）。随后是四级分级表：🔴 必须改 / 🟡 语义变化 / 🟢 仅观感/可观察回归 / ⚠️ 已知未修，每行注明判定依据来源（底稿编号）。读者 30 秒内要能判断"这次升级对我是什么量级的事"。

### 1. 升级步骤 checklist

分步执行，**每步带验收标准**（能判定过/不过的标准，不是"确认没问题"这种空话）。标准骨架：

```
Step N：<动作>
  验收：<可判定的标准>（如：build 通过 0 error / console 无 X 告警 / 截图与基线对比无 X）
```

前几步固定为：摸底（grep 现有用法 + **升级前留基线**——基线必须在旧版本上采集：前端截图/测试绿度，后端接口响应样本/性能指标，服务器配置快照）→ 升级依赖 → 引入/配置改造 → 类型/接口检查 → 策略决策（主题/配置/迁移）→ 验收回归 → 可观察面观察（console/日志/监控）。记录升级前**已经红的测试**，避免事后误归因给升级。

### 2. 代码改造对照表

`旧写法 → 新写法 → 原因` 三列表。若条目有共性，提炼一条可执行的判断规则放在表前（规则比逐条记忆可靠）；散例则逐条列。

### 3. 官方破坏性变更全表

每条：**变更内容 / 谁会中招 / 回退开关或修法**。特别注意收录 changelog `[Break]` 里有、升级指南没写的条目——这是调研的增量价值所在。

### 4. 人工验收清单

用户验证手段为纯人工时，这是最后的安全网。按高频坑排序、可打勾的清单形式。**形式随域取**：
- 前端：按页面/图表类型分组，每项附"发现异常 → 用哪个回退开关"
- 后端：按接口/可观察指标分组（日志、延迟、错误率、队列行为）
- 服务器/系统：按演练项分组（启动、健康检查、回滚演练）

### 5. 已知未修问题

目标版本 open 的、会影响升级决策的 bug：症状 / issue 编号 / 绕过方案。安全修复类（CVE/XSS）单独强调——它可能是"必须升到目标版本而非中间版本"的理由。

### 6. 生态兼容速查（有耦合库时）

矩阵表：库 × 支持状态 × 最低要求版本 × 安装风险。附安装摩擦的解决方案。

### 7. 不可逆变更的迁移方案（若有）

单向门清单：涉及数据/存储格式/协议变更时，给出迁移步骤、双向兼容期（新旧版本共存窗口）、演练环境验证记录、以及"不迁移会怎样"的后果。**没有恢复方案的单向门必须升级为用户决策点**，不允许默认执行。

### 8. 升级收益 + 回滚策略

收益清单（为什么要升）。回滚策略必须覆盖三层：
- **代码回滚**：改回去的写法对新旧版本是否都有效（前向兼容的改造可以只回版本号）
- **数据/产物回滚**：持久化数据、生成文件、缓存可能让旧版本无法安全恢复——单向门要提前标出
- **服务回滚**（服务器/后端域）：灰度/回滚窗口、混跑兼容期、回滚演练已验证

### 附录

- 新弃用清单（顺手清理项，标注"非阻塞"）
- 调研底稿索引（`research/` 各文件一行摘要 + 证据分级标记 ✅/📄/⚠️）
- 关键信源 URL 清单

## 文风纪律

- 每个事实断言可溯源（文末底稿索引或行内链接）
- 未验证的内容显式标 ⚠️，**不写没有证据的"应该没问题"**
- 反面警示：调研中发现的 AI 幻觉文章/假工具，写进文末提醒读者甄别（这是对用户文档可信度的保护）
